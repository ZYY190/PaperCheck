## 一、需求分析

程序需要读入两份文本文件——原文与经过增、删、改的抄袭版论文——并输出重复率。约束如下：

- 输入输出全部走**命令行参数 + 文件**，不读标准输入、不写标准输出以外的额外文件；
- 三个参数依次是原文路径、抄袭版路径、答案文件路径，均为绝对路径且不含空格；
- 答案文件中是保留两位小数的浮点数；
- 单次运行必须在 5 秒内结束，内存占用不超过 2048 MB，不允许连接网络；
- 进程不能异常退出（包括“文件不存在”“参数个数不对”这类可预期错误）。

由此提炼出三条设计底线：**结果要可解释、速度要有硬上界、错误要可控**。

## 二、算法设计

### 2.1 为什么不是“整篇直接比对”

最直观的做法是把两篇文章的全部字符拿出来做一次最长公共子序列（LCS），
用 `LCS 长度 / 抄袭版长度` 作为重复率。它的时间与空间复杂度都是 `O(n × m)`：
10 万字符的文档需要约 100 亿次比较，实测已经超过 16 秒，远超 5 秒时限。

### 2.2 实际采用的算法

把「重复率」定义为：**抄袭版中有多少比例的字符，能够在原文里找到顺序一致的对应**。
这个定义是单向的：抄袭版里新写的内容不算重复，抄来的内容才算重复，符合查重业务的语义。

计算分为五步：

1. **规范化**：去掉 BOM 与控制字符，全角转半角，英文转小写，统一换行符。
   这一步让“同一个字的不同写法”不再影响结果。
2. **分句**：按句末标点切分成句子；单句超过 100 个字符时再按逗号等停顿标点细切，
   仍然超长则按固定窗口兜底切分。分句把 `O(n × m)` 的平方级开销限制在「句长 × 句长」之内，
   使单次比对的代价有了上界。
3. **建索引**：对原文的每个句子建立**二元字组（bigram）倒排索引**，
   即「连续两个字」到「出现过它的句子编号」的映射。
4. **候选筛选**：对抄袭版的每一句，先统计它每个字组在原文中的词频，
   **按词频升序处理**——先看像「需求规格」这样的稀有字组（倒排表很短、区分度极高），
   后看像「的是」这样的通用字组（倒排表很长、几乎没有区分度）。
   稀有字组优先可以让有限的扫描预算花在最有价值的信息上。
5. **精确比对**：把候选句按命中字组数从大到小排列，逐个用 LCS 精确计算公共子序列长度，
   取最大值作为该句的重复字符数。最终
   `重复率 = Σ 各句匹配字符数 / 抄袭版特征字符总数`。

### 2.3 关键剪枝：一个严格成立的上界

长度为 `L` 的公共子序列一定包含 连续的 `L-1` 对相邻字符，而每一对都必然同时出现在两句话里。
因此有：

```text
LCS(抄袭句, 候选句) ≤ 抄袭句中「出现在候选句里的字组个数」+ 1
```

实现时把它写成 `min(较短句长, 命中字组数 + 尚未统计的字组数 + 1)`。
候选句已按命中数降序排列，因此一旦上界不超过当前最优值，后面的候选句就不可能更好，可以直接终止。

这个上界是**严格成立**的（不是启发式估计），所以剪枝不会损失准确率；
实测中它与「精确解的暴力算法」相比误差小于 1%。

### 2.4 类与职责

| 类 | 职责 |

| `Main` | 命令行入口。校验参数、串起流程、把异常翻译成退出码 |
| `PaperCheckException` | 自定义受检异常，携带错误码（E001–E007） |

| `NGramIndex` | 二元字组倒排索引（开放地址法的原始类型哈希表） |
| `LcsMatcher` | 最长公共子序列计算（两行滚动数组） |
| `SimilarityCalculator` | 算法编排：候选筛选、剪枝、结果汇总 |

### 2.5 复杂度

设抄袭版字符数为 `n`，平均句长为 `ℓ`，每句平均扫描的字组倒排表长度为 `d`：

- 建索引：`O(m)`，`m` 为原文字符数；
- 候选筛选：`O(n / ℓ × (ℓ log ℓ + d))`，其中 `ℓ log ℓ` 来自每句对字组的词频排序；
- 精确比对：每句最多 `MAX_LCS_PER_SENTENCE` 次 LCS，每次 `O(ℓ²)`。

所有环节都被常数上限约束，因此总耗时随文本规模**近似线性增长**。

## 三、异常处理设计

程序中的所有可预期错误都用 `PaperCheckException` 表达，并带一个错误码。
异常不会以堆栈形式暴露，而是打印成一行人类可读的提示，同时返回约定的退出码。

| 错误码 | 含义 | 触发场景 | 退出码 |
| --- | --- | --- | --- |
| E001 | 命令行参数个数不正确 | 参数少于或多于 3 个 | 2 |
| E002 | 输入文件不存在 | 路径写错、文件被删除、路径为空 | 3 |
| E003 | 路径指向的不是普通文件 | 传入了一个目录 | 3 |
| E004 | 文件读写失败 | 权限不足、文件被其它进程占用 | 3 |
| E005 | 文件编码无法识别 | 字节流既不是合法 UTF-8 也不是合法 GBK | 3 |
| E006 | 文件体积超过上限 | 单个输入文件超过 64 MB | 3 |
| E007 | 答案文件路径非法 | 答案路径是目录、父目录无法创建 | 3 |
| — | 未预期的内部错误 | 兜底捕获 `RuntimeException` | 4 |

设计上刻意做了两点区分：

1. **可预期错误不崩溃**。评测程序把「异常退出」视为失败，因此所有可预期场景都以
   正常返回 + 非零退出码收尾，绝不抛出未捕获异常。
2. **空内容不算错误**。原文或抄袭版为空、只有标点、只有空白时，结果就是 `0.00`，
   而不是报错——这更符合「没有重复」的业务含义。

## 五、性能改进

基准测试见 `docs/performance.md`，一键复现：

```bat
run-benchmark.bat
```

主要优化措施：

1. **从「整篇比对」改为「分句 + 候选筛选」**：这是数量级的改进，
   10 万字符从 16 秒降到 0.04 秒。
2. **原始类型倒排索引**：用开放地址法的 `long → int[]` 哈希表替换 `HashMap<Long, List<Integer>>`，
   查询路径零装箱、零对象分配。
3. **时间戳数组代替清零**：候选命中计数用「时间戳 + 计数数组」实现，
   省掉了每个句子对整张计数表的初始化。
4. **计数排序**：命中数取值范围很小，用计数排序替代比较排序，既线性又不产生临时对象。
5. **短路与剪枝**：完全相同的句子直接命中，不做 LCS；用严格成立的上界提前终止候选遍历。

优化后 100 万字符的文档耗时约 **0.93 秒**，重复率与暴力精确解一致（误差 < 1%）。
