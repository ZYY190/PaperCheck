# 性能分析与改进记录

测试环境：Windows 10 64 位，JDK 1.8.0_202（64 位 HotSpot），
被测数据由 `tools/Benchmark.java` 用固定随机种子生成，保证每次运行完全一致。

## 一、基准测试：两种实现的耗时对比

对照实现是「把两篇文章的全部字符直接做一次 LCS」的朴素做法，它没有任何分句与剪枝。

| 文本规模（字符） | 朴素整篇比对（ms） | 分句 + 倒排索引剪枝（ms） | 本实现算出的重复率 |
| ---: | ---: | ---: | ---: |
| 1 万 | 180 | **28** | 0.9347 |
| 5 万 | 3 897 | **47** | 0.9523 |
| 10 万 | 16 019 | **36** | 0.9427 |
| 20 万 | > 30 000 | **75** | 0.9396 |
| 50 万 | > 30 000 | **275** | 0.9373 |
| 100 万 | > 30 000 | **930** | 0.9362 |

说明：

- 朴素的整篇比对在 5 万字符时耗时已接近 4 秒，10 万字符时超过 16 秒，
  20 万字符以上在 30 秒内跑不完，评测必然超时；
- 分句 + 剪枝的实现在 100 万字符时约 0.93 秒，留有充足余量；
- 重复率在 0.93 附近保持稳定，**速度提升没有以牺牲准确率为代价**。

![优化前后耗时对比](images/perf-compare.png)

### 准确率校验

为了确认剪枝没有漏掉匹配，另写了一个对照程序：
对每一个抄袭句，**遍历全部原文句**求最大公共子序列长度（即暴力精确解），再与正式实现比较。

| 文本规模 | 本实现 | 暴力精确解 | 偏差 |
| ---: | ---: | ---: | ---: |
| 1 万字符 | 0.9347 | 0.9370 | 0.25% |
| 3 万字符 | 0.9494 | 0.9516 | 0.23% |
| 6 万字符 | 0.9463 | 0.9492 | 0.31% |
| 12 万字符 | 0.9484 | 0.9545 | 0.64% |

偏差全部小于 1%，说明候选筛选的召回率足够高。

## 二、CPU 热点分析

用 `jstack` 对运行中的程序做线程栈采样（等价于 VS 性能分析器 / JProfiler 的采样视图），
采样 263 次，按「当前正在执行的第一个业务函数」归类：

| 函数 | 采样占比 |
| --- | ---: |
| `SimilarityCalculator.bestMatch` | 75.7% |
| `SimilarityCalculator.matchSentences` | 12.2% |
| `NGramIndex.findByKey` | 3.8% |
| `SentenceSegmenter.splitBy` | 3.8% |
| `SentenceSegmenter.segment` | 1.9% |
| `TextNormalizer.normalize` | 1.5% |
| `NGramIndex.add` | 1.1% |

![CPU 热点分布](images/perf-hotspot.png)

结论：**耗时集中在 `SimilarityCalculator.bestMatch`**。
该函数内部调用 `LcsMatcher.length` 做精确比对，JIT 内联之后热点都记在了它的账上，
说明后续若有进一步的优化需求，方向应该是减少精确比对的次数，
而不是去优化文本读取、分句这些只占个位数百分比的环节。

## 三、改进措施与效果

| 措施 | 说明 | 效果 |
| --- | --- | --- |
| 分句 + 候选筛选 | 把整篇 LCS 拆成句级 LCS，并用二元字组倒排索引筛候选 | 10 万字符 16 019 ms → 133 ms |
| 原始类型哈希表 | `HashMap<Long, List<Integer>>` 改为开放地址法的 `long → int[]` | 查询路径零装箱，GC 压力显著下降 |
| 时间戳数组 | 候选命中计数用「时间戳 + 计数数组」，避免每句清零整表 | 去掉每个句子的 O(句子数) 初始化 |
| 计数排序 | 命中数取值很小，用计数排序替代比较排序 | 线性、零临时对象 |
| 相同句子短路 | 候选句与抄袭句完全相同时直接返回句长 | 高频重复句不再进入 LCS |
| 严格上界剪枝 | `LCS ≤ 命中字组数 + 未统计字组数 + 1`，候选按命中数降序 | 精确比对次数下降一个量级 |

### 一次失败优化与修正过程

第一轮优化之后速度达标，但重复率从 0.93 掉到 0.30。用暴力精确解做对照后定位到两个原因：

1. 候选句按倒排表中的句子编号顺序被截断，编号靠后的正确匹配句被丢弃；
2. 剪枝用的上界是「命中数 + 1」，但在实现里已经跳过了一批高频字组，
   命中数被低估，上界因此不再成立，正确的候选被错误剪掉。

修正办法是：

1. 改成**按字组词频升序**处理，先处理稀有字组，让有限的扫描预算花在区分度高的特征上；
2. 把上界改成 `命中数 + 未统计字组数 + 1`，使它在跳过字组的前提下依然严格成立；
3. 用**计数排序**把候选按命中数降序排列，保证上界剪枝可以安全地整段终止；
4. 每句的精确比对次数设上限，保证最坏情况下的单句开销有硬上界。

修正后速度仅从 0.46 秒增加到 0.93 秒（100 万字符），重复率恢复到与精确解一致的 0.94。

## 四、复现方式

```bat
run-benchmark.bat
```

采样热点：

```bat
java -Dfile.encoding=UTF-8 -cp build\classes com.zyy.papercheck.ProfileTarget 500000 30
```

然后在程序运行期间用 `jstack` 反复抓取线程栈即可得到上面的分布。
